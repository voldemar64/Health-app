# Архитектура Health App

Дата: 2026-11-08. Подтверждены Kotlin, монорепозиторий и готовая офлайн-модель на телефоне. Структура ниже — проект первой реализации; исполняемый код ещё не создан.

## Развёртывание и сервисы

Первая версия развёртывается как одно Android-приложение. База Room, речевая модель и бизнес-логика находятся на устройстве. Серверных сервисов и межсервисного HTTP нет.

Внутренние компоненты приложения:

| Компонент | Владелец | Ответственность |
| --- | --- | --- |
| PressureRepository | domain: контракт; data: реализация | Измерения и выборки для статистики |
| MedicationRepository | domain: контракт; data: реализация | Лекарства, версии расписаний, отметки приёма |
| CommandParser | domain | Текст в команду, черновик или запрос уточнения |
| SpeechRecognizer | domain: контракт; speech: реализация | Звук в промежуточный и окончательный текст |
| SpeechOutput | domain: контракт; speech: реализация | Озвучивание подтверждения |
| ReminderScheduler | domain: контракт; reminders: реализация | Установка, отмена и восстановление сигналов |
| VoiceSessionController | app | Состояние голосового диалога и подтверждение |

Это Kotlin-компоненты, а не независимые процессы. Android `Service` не нужен для обычной короткой голосовой сессии в открытом приложении. Фоновое прослушивание потребует отдельного решения.

## Модули и зависимости

```text
:app
  ├── :core:domain
  ├── :core:data ────────────────→ :core:domain
  ├── :platform:speech ──────────→ :core:domain
  └── :platform:reminders ───────→ :core:domain
```

`app` собирает зависимости и управляет UI. `domain` содержит сущности, проверки, расчёт повторов, разбор команд, use cases и интерфейсы адаптеров. `data` хранит данные. `speech` и `reminders` изолируют Android и сторонние SDK. Направление стрелок означает зависимость при сборке.

Room — источник сохранённых пользовательских данных. Экраны подписываются на `Flow` репозиториев через ViewModel и получают `StateFlow` состояния. Временные черновики живут отдельно от сохранённых записей. Ручной и голосовой ввод используют одинаковые проверки и use cases.

Подход согласуется с рекомендациями Android по [модулям](https://developer.android.com/topic/modularization/patterns) и [локальному источнику данных](https://developer.android.com/topic/architecture/data-layer/offline-first).

## Данные и инварианты

| Сущность | Основные поля | Правило |
| --- | --- | --- |
| PressureMeasurement | id, systolic, diastolic, pulse?, measuredAt, recordedZoneId, note? | Давление — отдельные целые значения; пульс необязателен |
| Medication | id, name, aliases | Название и подтверждённые пользователем голосовые варианты |
| MedicationSchedule | id, medicationId, revision, dose, recurrence, localTime, startDate, endDate?, zoneId | Количество, единица и повтор задаются явно |
| IntakeRecord | id, scheduleId, scheduleRevision, occurrenceKey, plannedAt, status, takenAt?, snapshot | История сохраняет название и дозу на момент события |

`Dose` хранит точное десятичное значение и единицу `TABLET`, `MG` или `G`. В Room значение сериализуется без потерь, например десятичной строкой. `Float`/`Double` для дозы не использовать. Количество таблеток не переводится в массу без явно заданного соответствия.

Повторы первой версии: `ONCE`, `DAILY`, `WEEKLY(dayOfWeek)`. Просмотр месяца не означает ежемесячный повтор. Будущие события вычисляются для выбранного интервала; бесконечный ряд записей заранее не создаётся.

Измерение и факт приёма хранятся как `Instant`. Расписание хранит локальные дату/время и IANA `zoneId`. Для первой версии предлагается сохранять часовой пояс расписания при поездках; его изменение выполняется явно. Это продуктовая политика, которую нужно проверить до реализации напоминаний.

При переходе летнего времени предлагаемая политика: несуществующее время сдвигается на длину пропуска, повторяющееся время срабатывает один раз по более раннему смещению. Политика централизована в калькуляторе повторов и покрывается тестами.

При изменении серии прошлые отметки сохраняются. Новые события получают новую ревизию расписания. `occurrenceKey` однозначно определяет событие внутри ревизии; уникальность в базе защищает от повторной отметки после двойного нажатия или повторной доставки действия уведомления.

## Поток голосового ввода

```text
Запуск пользователем → разрешение микрофона → загрузка локальной модели
→ окончательный текст → CommandParser → черновик / уточнение
→ визуальное и при необходимости голосовое подтверждение
→ общий use case → Room → обновление UI
```

Промежуточный текст показывается пользователю, но не выполняет команду. Навигация может выполняться сразу; добавление, изменение, удаление и отметка приёма требуют явного подтверждения. Неполная команда не получает выдуманные название, дозу или время.

Состояния сессии: `Idle`, `Preparing`, `Listening`, `Parsing`, `NeedsClarification`, `AwaitingConfirmation`, `Saving`, `Completed`, `Error`. Отмена очищает черновик. Уход приложения в фон завершает запись; возвращение не возобновляет микрофон автоматически. Повторное подтверждение не должно приводить к второй записи.

Названия сопоставляются с личным списком лекарств. Неоднозначные совпадения дают выбор. Новое название показывается для подтверждения, неизвестное слово не заменяется молча похожим. Уверенность распознавателя служит подсказкой, а не доказательством правильной дозировки.

Во время озвучивания микрофон приостановлен, чтобы приложение не распознало собственный ответ. Для следующего ответа пользователя начинается новая фаза прослушивания в рамках открытой сессии.

## Контракт речевого адаптера

Ниже эскиз API, не готовая реализация. Типы принадлежат `domain`; публичный API не содержит классов Vosk или Android.

```kotlin
interface SpeechRecognizer {
    val events: Flow<RecognitionEvent>
    suspend fun prepare(): PreparationResult
    suspend fun start(): StartResult
    suspend fun stop()
    suspend fun cancel()
    suspend fun release()
}

sealed interface RecognitionEvent {
    data class Partial(val text: String) : RecognitionEvent
    data class Final(val text: String) : RecognitionEvent
    data class Failed(val reason: RecognitionFailure) : RecognitionEvent
    data object Ended : RecognitionEvent
}

interface CommandParser {
    fun parse(text: String, context: CommandContext): ParseResult
}
```

`prepare` возвращает `Ready`, `ModelMissing`, `ModelInvalid` или ошибку ресурсов. `start` возвращает результат запуска, включая отказ разрешения, занятый микрофон и уже активную сессию. Отсутствие речи и ошибка движка представлены явными событиями.

`stop` завершает ввод с возможным окончательным результатом; `cancel` отбрасывает результат. Подписка на события устанавливается до `start`. Одновременно разрешена одна сессия. Адаптер должен доставлять окончательный результат активному подписчику без потерь, помечать сессии внутренним идентификатором и отбрасывать поздние callbacks после отмены.

Загрузка модели, нативный inference и освобождение ресурсов не блокируют главный поток. Модель может переиспользоваться между сессиями; recognizer и микрофон освобождаются по окончании сессии. Переход на sherpa-onnx меняет адаптер и поставку модели, сохраняя UI, парсер и базу.

`CommandContext` содержит текущий экран, черновик диалога, переданный Clock/часовой пояс и разрешённый список лекарств. Парсер возвращает команду, черновик, запрос уточнения или отказ; сам не пишет в базу.

## Поставка модели

Первый кандидат — Vosk с `vosk-model-small-ru-0.22`; выбор для выпуска зависит от замеров. Исходные веса не обучаем. Подробности — в [карточке модели](../models/vosk-ru/README.md).

На этапе сборки отдельная явная подготовка скачивает фиксированный архив, проверяет SHA-256 и помещает модель в генерируемые assets. Обычная Gradle-сборка использует подготовленный локальный артефакт; при его отсутствии выдаёт понятную ошибку. В Git хранятся метаданные, будущий скрипт подготовки, лицензии и зафиксированная контрольная сумма, но не веса.

Установочный пакет содержит модель. При первом запуске она копируется в приватное хранилище приложения вне резервного копирования через временный каталог с последующим атомарным переключением. Маркер готовности записывается только после успешной подготовки. Оборванная установка не считается готовой; повторная подготовка безопасна.

Работающая версия модели сохраняется до успешной установки новой. Версия модели и версия native-библиотеки фиксируются раздельно и проверяются вместе. Интернет на телефоне для базовой функции не нужен, сетевой fallback отсутствует. В первой версии обновление модели приходит с обновлением приложения.

## Расписание и напоминания

Календарь — данные и расчёт повторов. Напоминания — необязательный побочный эффект после сохранения расписания; отказ разрешения не отменяет запись расписания.

При изменении расписания транзакция Room сохраняет данные и признак необходимости пересчёта сигналов. Планировщик применяет изменения идемпотентно и подтверждает обработанную ревизию. При новой ревизии во время обработки пересчёт остаётся необходимым. Это закрывает окно сбоя между сохранением данных и вызовом AlarmManager.

Для точного времени планировать ближайшее одноразовое событие каждого активного расписания, затем следующее. Идентичность `PendingIntent` определяется расписанием; отмена и замена устойчивы к повторному вызову. Получатель проверяет актуальную ревизию перед уведомлением. Просроченный сигнал не означает, что лекарство принято.

Пересчёт выполняется после изменения расписания, запуска приложения, перезагрузки, обновления приложения, изменения системного времени и восстановления доступа к точным сигналам. Принудительная остановка приложения и отключённые уведомления требуют отдельной обработки в UI.

WorkManager подходит для отложенного восстановления согласованности, но не задаёт точное время приёма. Для AlarmManager проверять доступ к точным сигналам; при его отсутствии явно показывать состояние напоминаний. Подробности ограничений: [Android alarms](https://developer.android.com/develop/background-work/services/alarms) и [разрешение уведомлений](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

## Данные и приватность

Аудио по умолчанию обрабатывается в памяти и не сохраняется. Транскрипты, названия препаратов и показатели не пишутся в технические логи. База находится в приватном хранилище приложения. Room сам по себе не означает шифрование базы.

Для первой версии исключить медицинскую базу и черновики из автоматического облачного backup; модель тоже не резервировать. Экспорт, перенос данных и дополнительное шифрование требуют отдельного решения. Удаление приложения без экспорта означает потерю локальных записей — это нужно объяснить пользователю.

## Проверка архитектуры

- JVM: числа, дроби, единицы, незавершённые и неоднозначные команды; календарь, DST, конец месяца, ревизии.
- Room: миграции, транзакции, уникальность отметок, точное хранение дозы, запросы статистики.
- UI: одинаковое сохранение ручного и голосового черновика, отмена, подтверждение и ошибки.
- Устройство: авиарежим с первого запуска, отзыв разрешения микрофона, прерывание сессии, повреждённая модель, память и задержка.
- Напоминания: перезагрузка, отказ разрешений, редактирование серии, двойная доставка и устаревший сигнал.

Ключевая метрика речи — точность всей записи: название, количество, единица, время и повтор. Отдельно измерять задержку и память на слабом устройстве. Порог выпуска утверждается после первого замера; текущая архитектура не обещает конкретную точность.
