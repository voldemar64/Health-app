# Правила разработки

## Ветки и pull requests

- `main` содержит объединённые изменения.
- Ветка называется по модулю и задаче: `android/bootstrap`, `domain/pressure-validation`, `data/room-storage`, `speech/vosk-integration`, `reminders/daily-schedule`, `docs/architecture`.
- Перед началом работы обновить `main`, затем создать рабочую ветку.
- Изменения публикуются в рабочую ветку, проходят PR и проверки, затем объединяются в `main`.
- Не обходить защиты веток и обязательные проверки. Не применять force push к `main`.
- Исключение для первоначально пустого репозитория: один пустой стартовый коммит создаёт базу `main` для первого PR.

## Коммиты и авторство

Использовать Conventional Commits, например `feat(speech): add offline recognition` или `docs(architecture): define application modules`.

Не включать названия ИИ-инструментов в ветки и коммиты. Не добавлять ИИ как collaborator, автора или `Co-authored-by`. Использовать настроенную Git-идентичность разработчика.

## Проверки

Для документации проверить ссылки, согласованность дерева и отсутствие утверждений о ещё не реализованной функциональности.

После появления сборки: проверять изменённые модули, выполнять Android lint и сборку debug. Речевые модели и напоминания дополнительно проверять на физических устройствах. В PR указывать выполненные проверки и оставшиеся ограничения.

В репозитории допускаются только искусственные примеры медицинских данных. Реальные записи, аудио пользователей, ключи подписи и локальные секреты не коммитить.
